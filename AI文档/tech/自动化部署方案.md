# 自动化部署方案

## 1. 目标

- 当代码推送到 `main` 分支时，自动部署后端服务
- 部署目标服务器为 Ubuntu 24.04
- 部署目录固定为 `~/api-todofairyV2`
- 部署方式使用 `docker compose`
- 生产环境变量通过 GitHub Secrets 下发

## 2. 部署流程

1. GitHub Actions 监听 `main` 分支推送
2. Workflow 打包仓库部署所需文件，排除 `.git`、`.github`、`node_modules`、`apps/miniprogram`、`data`、`coverage`
3. Workflow 将部署包写入 GitHub Actions runner 临时目录，再通过 SSH/SCP 上传到服务器 `~/api-todofairyV2`
4. Workflow 在服务器写入 `.env.production`
5. Workflow 在服务器执行 `docker compose -f docker-compose.deploy.yml build --pull`
6. Workflow 在服务器执行 `docker compose -f docker-compose.deploy.yml run --rm api pnpm --filter @todo-fairy/api prisma:migrate:deploy`
7. Workflow 在服务器执行 `docker compose -f docker-compose.deploy.yml up -d api`

## 3. 仓库内文件

- Workflow：`.github/workflows/deploy-api.yml`
- 后端镜像：`apps/api/Dockerfile`
- 部署编排：`docker-compose.deploy.yml`
- 镜像构建忽略：`.dockerignore`

## 4.1 打包约束

- 部署包文件名固定为 `deploy-bundle.tar.gz`
- 部署包必须生成到 runner 临时目录，不能直接写回仓库根目录
- 原因是 `tar -czf ... .` 在读取当前目录 `.` 的同时，如果把输出文件写回当前目录，会导致目录元数据变化并触发 `tar: .: file changed as we read it`

## 5. GitHub Secrets

- `DEPLOY_HOST`：服务器 IP 或域名
- `DEPLOY_PORT`：SSH 端口
- `DEPLOY_USER`：SSH 用户名
- `DEPLOY_SSH_KEY`：SSH 私钥内容
- `PROD_DATABASE_URL`：生产数据库连接串
- `PROD_JWT_SECRET`：生产 JWT 密钥
- `PROD_WECHAT_APPID`：生产环境微信 AppID
- `PROD_WECHAT_SECRET`：生产环境微信 Secret
- `PROD_INTERNAL_API_KEY`：生产环境内部接口密钥
- `FEISHU_ROBOT_WEBHOOK`：飞书自定义机器人地址，保存于仓库或 `main` 环境的 GitHub Secrets；不得写入代码、文档或日志

## 6. 运行时环境变量

Workflow 会在服务器上写入 `.env.production`，至少应包含以下变量：

```env
PORT=3000
DATABASE_URL=mysql://user:password@127.0.0.1:3306/tasksprite
JWT_SECRET=replace_me
JWT_EXPIRES_IN=7d
WECHAT_APPID=replace_me
WECHAT_SECRET=replace_me
INTERNAL_API_KEY=replace_me
NODE_ENV=production
```

### 6.1 飞书部署通知（2026-11-02）

自动部署工作流 `.github/workflows/deploy-api.yml` 仅通过飞书发送部署通知，原企业微信部署通知引用已移除。飞书机器人地址读取 `secrets.FEISHU_ROBOT_WEBHOOK`，由维护者在 GitHub 中配置，不下发到服务器 `.env.production`。

| 触发时机 | 飞书卡片标题 | 标题颜色 |
|---|---|---|
| 开始部署 | 任务精灵：开始部署 | 蓝色 `blue` |
| 既有部署步骤全部成功 | 任务精灵：部署成功 | 绿色 `green` |
| 工作流部署步骤失败 | 任务精灵：部署失败 | 红色 `red` |

卡片使用飞书交互卡片2.0结构，正文显示提交编号、触发人、部署详情链接，并提供“查看部署详情”按钮。成功和失败沿用原有 `success()`、`failure()` 条件；取消执行仍不单独通知。此处“部署成功”表示现有部署步骤返回成功，不新增线上健康验收步骤。

部署前的清理不再执行删除服务器全部已停止容器的命令，避免影响其他项目保留的回滚或备份容器。数据库迁移的临时容器继续由 `docker compose run --rm` 自行移除。

三处通知在现有步骤内直接发送，均设置20秒请求超时，并检查HTTP请求、JSON解析及飞书业务返回码（`code=0`，兼容旧字段 `StatusCode=0`）。地址未配置、网络失败、返回格式错误或返回码非零时，输出明确警告并让该通知步骤返回失败；保留 `continue-on-error: true`，通知异常不阻断部署。日志不输出机器人地址或原始响应内容。

配置更改需合并到 `main` 才会用于正式部署；该合并同时触发现有自动部署流程。开发阶段只进行离线验证，不单独发送群聊测试消息；正式发布须由用户授权合并及推送 `main`。2026-11-02用户已授权发布v0.9.3，先推送功能分支，再合并及推送 `main`，最后切回原功能分支。离线验证命令：`python -m unittest discover -s deploy/tests -p "test_feishu_notifications.py" -v`，需要本地Python与PyYAML。

## 7. 迁移约束

- 生产环境只允许执行 `prisma migrate deploy`
- 不允许在生产环境使用 `prisma db push`
- 必须先提交 Prisma migration 文件，再允许进入自动部署流程

## 8. 风险与约束

- `main` 分支的每次推送都会触发部署，因此 `main` 必须保持可发布状态
- 服务器需预先安装 Docker 与 Docker Compose 插件
- 服务器 SSH 用户需对部署目录和 Docker 具备执行权限
- 数据库变更失败会导致部署中断，避免未验证的 migration 直接进入 `main`
- 如果修改部署包生成位置或归档文件名，必须同步修改工作流上传步骤与本文档

### 9.1 线上即时调整与验证

1. 修改前，在 `/root/source-config-backups/<时间戳>/` 备份 Docker 安装源、服务器上的 Dockerfile，以及当前容器原有的 npm 全局配置（若不存在则记录不存在）；备份目录仅允许 root 访问。
2. 仅将 Docker 安装源地址改为阿里云，保持 `signed-by`、架构及 `noble stable` 不变；定向更新此源的索引，验证签名校验和下载成功，不安装或升级 Docker。
3. 在现有 `todo-fairy-api` 容器中执行 `npm config set registry https://registry.npmmirror.com --location=global`。验证 npm、pnpm 查询结果及 npm 镜像可访问性；该容器调整无需重启，但单独重建容器会丢失，因此必须同步下一步。
4. 服务器构建目录及本地 Dockerfile 两个阶段均增加 `NPM_CONFIG_REGISTRY`。本次不构建、不部署新镜像；后续正常部署时，新容器将从镜像环境变量继承 npm 默认源。
5. 比对调整前后所有运行容器的标识和启动时间，确认未重启；检查任务精灵健康接口。

### 9.2 回退与范围

- 将备份的 `docker.list`、Dockerfile 还原至原路径；容器内 npm 全局配置原来存在则还原，原来不存在则仅移除此次新增的全局 `registry` 配置项。回退后重新查询源地址。
- 本次不修改 Docker 镜像加速器、不重启 Docker、不部署应用、不修改其他应用容器，也不进行磁盘清理或创建 Swap。
- 宿主机未安装 Node/npm/pnpm，无需为宿主机新增这些软件。业务接口及数据结构无变化。

## 10. 磁盘维护与 Swap（2026-11-02）

### 10.1 维护规则及配置文件

| 项目 | 规则 | 仓库文件及服务器位置 |
|---|---|---|
| 构建缓存 | 每天北京时间04:30清理超过168小时未使用的构建缓存；以保留2 GiB为目标，不强删近期或仍被引用的缓存 | `deploy/maintenance/docker-cache-maintenance.service`、`.timer` 安装到 `/etc/systemd/system/` |
| 系统日志 | 磁盘日志目标不超过200 MiB，最长保留14天；达到容量目标时可能更早清理历史日志 | `deploy/maintenance/90-task-fairy-retention.conf` 安装到 `/etc/systemd/journald.conf.d/` |
| Swap | `/swapfile` 独占1 GiB磁盘空间，文件权限600；`/etc/fstab` 增加 `/swapfile none swap sw,nofail 0 0`，开机自动启用 | Swap文件首次由管理员创建，已有Swap或同名文件时不得覆盖 |
| Swap使用倾向 | `vm.swappiness=10`，已即时生效并持久化 | `deploy/maintenance/99-task-fairy-swap.conf` 安装到 `/etc/sysctl.d/` |

缓存清理命令为 `docker builder prune --all --filter until=168h --keep-storage 2147483648 --force`。使用文件锁避免重复执行，以较低进程和磁盘优先级运行。2 GiB是结合年龄过滤的保留目标，并非整个Docker目录的硬性上限；共享层、近期使用或仍被引用的内容会继续占用空间。

定时任务使用 `Persistent=true`，关机错过执行时间后，恢复时补执行。安装或修改维护配置后，应先运行 `systemd-analyze verify` 验证，再执行 `systemctl daemon-reload`，启用 `docker-cache-maintenance.timer`。应用发布流程不自动重新安装这些宿主机配置。

### 10.3 运维检查与回退

- 查看缓存任务：`systemctl status docker-cache-maintenance.timer`、`systemctl show docker-cache-maintenance.service -p Result -p ExecMainStatus`；查看磁盘与Swap：`df -h /`、`swapon --show`、`free -h`。
- 查看配置实际值：`systemd-analyze cat-config systemd/journald.conf`、`sysctl vm.swappiness`；查看Swap开机配置：`findmnt --fstab --types swap`及`systemctl show swapfile.swap -p FragmentPath`。
- 停止定期清理时停用对应timer，并移除本次新增的service和timer后重新加载systemd；日志策略回退仅移除本次新增的drop-in，再重启日志服务。被清理的旧缓存可在构建时重建，已删除的历史日志无法恢复。
- 回退Swap前必须先核实当前可用物理内存能够容纳已换出的内容，再执行 `swapoff /swapfile`；成功停用后再移除本次fstab条目、Swap文件及sysctl配置，恢复备份记录中的原始使用倾向。不可在已启用状态直接删除Swap文件。
