# 总体技术方案

## 1. 架构目标

将任务精灵重构为标准 Monorepo：

- `apps/api`：NestJS 后端服务
- `apps/miniprogram`：原生微信小程序
- `packages/*`：后续共享类型、常量、工具

## 2. 技术选型

- 后端：Node.js + NestJS + Prisma + MySQL
- 前端：原生微信小程序
- 契约：REST + OpenAPI
- 鉴权：JWT
- 校验：class-validator

## 3. 当前实现

### 3.1 数据层

当前后端已不再使用 `data/dev-db.json` 文件存储，统一改为 `Prisma + MySQL`：

- Prisma schema：`apps/api/prisma/schema.prisma`
- 数据连接：根目录 `.env` 中的 `DATABASE_URL`
- 初始化方式：`pnpm install` 后执行 `pnpm run prisma:push`

### 3.2 已完成模块

- `auth`：微信登录、开发态登录、JWT 签发
- `tags`：标签增删改查
- `tasks`：任务增删改查、任务统计
- `todos`：待办生成、状态切换、补偿、父子待办联动
- `calendar`：月历状态统计
- `notifications`：通知设置、测试发送、预览、日志
- `internal`：日切、日报、周报、数据库初始化信息

## 4. 关键约束

- 父任务统计口径不能回退
- 周报自动发送仍只允许周一执行
- 一次性任务创建后按指定待办日期生成待办，保留原有自动归档语义
- 子待办全部完成后，父待办自动完成
- 所有用户侧资源访问必须经过 JWT 和 `userId` 归属校验
- GitHub Actions 部署通知读取 `FEISHU_ROBOT_WEBHOOK`，开始、成功、失败分别使用蓝、绿、红飞书卡片，标题为“任务精灵：开始部署/部署成功/部署失败”；通知异常记录警告但不阻断部署，具体见《自动化部署方案》第6.1节。
- npm、pnpm、Corepack 及系统软件使用阿里云国内源；Dockerfile 构建和运行阶段统一设置 npm 默认源。Node、MySQL 基础镜像暂保留 DaoCloud 国内源，具体地址及回退方式见《自动化部署方案》第9节。
- 宿主机每日北京时间04:30清理超过7天未使用的构建缓存，目标保留2 GiB；系统日志目标200 MiB且最长14天。宿主机配置1 GiB文件型Swap及`vm.swappiness=10`，具体实施记录和回退方式见《自动化部署方案》第10节。缓存目标不等于整个Docker目录的容量上限。

## 5. 定时任务方案

当前内部接口保留以下能力，供后续调度器接入：

- `POST /api/v1/internal/daily-rollover`
- `POST /api/v1/internal/daily-summary-notify`
- `POST /api/v1/internal/weekly-summary-notify`
- `POST /api/v1/internal/db-init`

调用时必须在请求头中传入 `x-internal-key`，并与环境变量 `INTERNAL_API_KEY` 一致。

### 5.1 一次性待办顺延（2026-11-02）

- 使用现有 `Asia/Shanghai` 每日01:00定时入口，先执行一次性待办顺延，再标记重复待办过期、生成重复待办。返回及日志增加 `oneTimeDeferred` 父待办数量。
- `classifyTodos` 按 `userId + parentTaskId` 批量查询所属任务，包括已归档任务；仅当明确存在空重复星期规则时，标记 `isOneTime=true`。无关联或无明确规则时维持原行为。无需数据库结构变更和历史类型回填。
- 每个父待办与全部有效子项在同一个串行化事务中更新日期，条件限定未删除、未完成、早于目标日期，保留状态和其他业务内容；并发冲突（P2034）最多重试两次，其他失败回滚并交给现有日切错误日志记录。未完成的一次性记录不进入过期标记。
- 待办列表、状态修改、编辑结果暴露 `isOneTime`；前端即时勾选、服务端月历、统计及通知统一排除未完成的一次性父待办，完成后正常计入；子项不独立计数。全部未完成一次性待办对应的月历状态为 `no_todo`（中性），列表仍展示这些待办。
- 一次性父待办完成（含子项全部完成触发）时，将整组日期归到北京时间当天；完成记录不再顺延。部分完成的子项跟随尚未完成的父项顺延，完成时间保持原值。
- 发布后首次01:00日切会处理全部已有积压记录。上线验证应检查顺延数量、原日期与目标日期列表、月历状态及日报预览；不需要手动回填或重新生成待办。
